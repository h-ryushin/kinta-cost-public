# セキュリティのしくみ

このアプリが、何をどう守っているか。2026-10-25 時点（秘密レシピの暗号化：D-148 を含む）。オーナーに説明するときにも使う。

## 1. 入り口（誰が入れるか）

| | 入り方 |
| --- | --- |
| URL を知っている人 | **ログインしないと何も見えない**。新規登録もできない（アカウントはオーナーが招待で作る：D-091） |
| オーナー（iPhone） | **顔・指紋（パスキー）だけ**。パスワードは打たない（D-086） |
| オーナー（PC など） | パスワード → オーナーの iPhone に出した6桁（D-138）。一度入ったら、その PC の顔・PIN（Windows Hello）を登録できる |
| オーナー（iPhone をなくした） | パスワード → 控えておいた復旧コード（D-139） |
| 社員 | メールとパスワード（8文字以上：D-117）。顔・指紋は使いたい人だけ（便利さのため：D-134） |

- 2時間使わない・タブを閉じる・ほかのページに1分以上離れると、ログインし直し（D-133・D-136）。
- 打ち間違いは10分に5回まで（6桁・復旧コード）。

### 顔・指紋の正体

- 顔や指紋のデータは iPhone の外に出ない。Supabase にも入っていない。
- 「顔・指紋を登録する」と、その端末の中に**鍵**が作られる。Supabase には、鍵が本物か確かめるための「公開の鍵」だけが入る。
- Supabase は誰の顔かを見ず、「登録された鍵で答えたか」だけを見る。つまり顔・指紋の正体は「**登録した端末を持っていること**」。
- だから、**新しい端末を誰が足せるか**が大事。オーナーの2つ目からの端末は、顔・指紋か iPhone の6桁・復旧コードで入っているときしか足せない。これは画面ではなくデータベースが守る（D-144）。パスワードを知っているだけの人は、自分の端末を足せない。

## 2. 権限はデータベースが守る

画面（JavaScript）は利用者の端末で動くので、書き換えられる前提で作っている。権限の判定はすべてデータベース（RLS）で行う。画面を改造しても、データベースが断る。

| 立場 | できること |
| --- | --- |
| 未ログイン | 何もできない |
| 停止した社員 | 何も読めない |
| 社員 | 材料・仕込み品・メニュー・創作レシピの登録と編集・削除（秘密のものは名前と金額だけ見える）。操作ログを見る（D-162） |
| オーナー | ＋秘密の中身・秘密にするかどうか、利用者の管理、設定 |
| オーナー（パスワードだけ） | 何も読めない（本人確認が済むまで通さない） |

`npm run test:db`（153件）で、毎回これを確かめている。

## 3. 秘密レシピ（塩だれなど）

配合（材料・使用量・メモ）は**暗号化して保存する**（D-148。オーナーの判断で「開発担当にも見られたくない」：D-145）。

- 暗号化と元に戻す作業は、オーナーの端末のアプリの中で行う。鍵は Supabase に送らない。
- レシピ鍵は、オーナーのパスキーが顔・指紋を通したときだけ返す秘密の値（WebAuthn PRF）か、控えておく「予備の鍵」（12文字：D-152）で開く。
- Supabase（オーナーのアカウントでも）・開発担当・毎晩のバックアップから見ても、配合は意味のない文字の並び。
- 暗号化するのは配合だけ。名前・売価・原価の金額は社員にも見せるので暗号化しない（D-002）。社員は、オーナーが計算した原価を見る。
- 開いた鍵は画面のあいだだけ持つ。読み込み直す・ログアウトすると閉じる。
- ログインのパスワードを鍵にしないのは、パスワードを Supabase に送っており、メールで決め直せるため。覚える合言葉にしないのは、忘れたら二度と開けず、短いと総当たりで開けられるため（D-005）。予備の鍵は覚えなくてよい（紙に控える）。
- **予備の鍵と、鍵を開けられる端末をすべてなくすと、配合は誰にも開けない。**

## 4. 開発担当にできること・できないこと

本番はオーナーのアカウントの Supabase と Cloudflare に置く（D-146）。そのうえで、開発担当は次のようになる。

| 頼まれること | 開発担当 |
| --- | --- |
| 画面の直し・機能の追加・公開 | できる（GitHub・Cloudflare。公開はオーナーの「公開して」のあと：D-049） |
| データベースの形を変える | できる（`main` に入ったら GitHub Actions がオーナーの Supabase に流す。鍵はオーナーが GitHub に登録：D-072） |
| 値段・メニューの打ち間違いを直す | できる（社員のアカウントでアプリから） |
| 社員の招待・停止・削除 | オーナーがやる |
| Supabase・Cloudflare の管理画面の設定 | オーナーに手順を渡す（`docs/supabase-settings.md`）か、メンバーとして招いてもらう |
| **秘密レシピの配合を見る・直す** | **できない**（暗号化してある） |

### 正直に書いておくこと：開発担当は技術的には「オーナー」になれる

- データベースを直す鍵を持つ人は、データベースの決まり（RLS）を飛び越えられる。開発担当が自分をオーナーにする・データを消す、を仕組みだけで完全に止めることはできない。どのシステムの開発担当も同じ。
- それでも、困ることは小さくしてある。
  1. **オーナーになっても配合は読めない。** 配合の鍵はオーナーの顔・指紋（と紙の予備の鍵）の中にあり、データベースの「オーナー」の印とは関係ない。
  2. **やればすぐばれる。** オーナーは1人だけ（D-090）。開発担当がオーナーになるにはオーナーを外すしかなく、外された時点でオーナーはオーナーの画面に入れなくなる。
  3. **オーナーになっても、できることは増えない。** 社員の管理・操作ログ・設定は、データベースの鍵を持つ時点で触れる。
  4. **オーナーがいつでも止められる。** Supabase と Cloudflare はオーナーのアカウントなので、データベースのパスワードと鍵を変えれば、開発担当は何もできなくなる。GitHub に変更の記録も残る。
- もっと固くしたいときは、開発担当にデータベースの鍵を**ずっとは持たせない**（データベースを変えるときだけオーナーが鍵を出し、終わったら消す）。代わりに、データベースを変えるたびにオーナーの手間が増える。画面の直しと公開には、データベースの鍵は要らない。
- 残る弱いところ：アプリを書き換えて公開できる人が悪いアプリを出すと、オーナーが配合を開いた瞬間に取られる。これは「公開はオーナーの承認だけ」と GitHub の記録で防ぐ。

## 5. 通信と公開しているアプリ

公開サイトに付けているヘッダー（`public/_headers`）：

```
strict-transport-security: max-age=31536000; includeSubDomains   … 常に HTTPS
content-security-policy: default-src 'self' …                     … 外部スクリプトを読まない（ページごと。D-155）
x-frame-options: DENY                                             … 他サイトに埋め込めない
x-content-type-options: nosniff
referrer-policy: strict-origin-when-cross-origin
permissions-policy: camera=(), microphone=(), geolocation=(), payment=()
x-robots-tag: noindex, nofollow                                   … 検索に出ない
```

- CSP（D-155）：ページの中に直接書いたプログラムは、書き出したときの中身の指紋（SHA-256）が一致するものだけを動かす（`'unsafe-inline'` は使わない）。つなぎ先は、このアプリの Supabase だけ。ページごとの CSP は `npm run build` のたびに `scripts/csp-headers.mjs` が作る。
- Cloudflare のログを有効にしている。1日1回の ping の成否も残る（D-155）。
- ブラウザに渡している Supabase のキー（anon）は公開前提の鍵。これだけでは何も読めない。
- `service_role` キー（全権限）はブラウザに渡さない。社員の招待の Edge Function の中だけで使う。
- パスワード・接続情報は `.env.local` と GitHub の Secrets に置き、Git には入れない。

## 6. バックアップ

- 毎晩4時ごろ、GitHub Actions がデータを書き出し、AES-256 で暗号化して30日分保管する（D-067）。
- 接続は読み取り専用のユーザー。漏れても書き換え・削除はできない。
- 復元を実際に試した（`docs/backup.md`）。
- 秘密レシピの配合は、バックアップの中でも暗号文のまま。

## 8. 困ったとき

- **社員が辞めた・端末をなくした** → 「利用者」で停止。その瞬間から何も読めない。
- **オーナーの iPhone をなくした** → パスワード＋復旧コードで入り、新しい端末を登録して復旧コードを作り直す（`docs/setup-owner.md`）。
- **データを壊した** → バックアップから戻す（`docs/backup.md`）。
- **誰が何をしたか知りたい** → 「操作ログ」。
